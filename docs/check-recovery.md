# Verification and local recovery

Verification holds a nonblocking POSIX file lock for the whole task check operation, including result attachment. A second verification, release or recovery is refused while that lock is held, including after the claim lease expires. Reassignment also checks operation state. Expiry alone never establishes that a worker stopped. There is no daemon or automatic recovery kill.

Private workspace `verification/<task>.json` stores a versioned attempt identity, controller PID, state and timestamps, and the child PID/process group once observed. It does not store owner tokens or check arguments. Atomic replacement and file/directory fsync persist transitions before launch and after observing the child. `launching` without a recorded child group is intentionally uncertain: the controller could have died between starting a child and persisting its identity. A hard-killed controller releases its lock but its child may remain alive.

`status` (also returned by `resume`) includes each task's `verification` observation. `verification-status <task>` provides the same focused, read-only observation. These commands create no operation files and disclose no token or raw arguments. `lock_held` and `observed_group_live` are momentary observations, not owner identity or authority certificates. Absent/unreadable metadata is distinguished from a known stopped attempt. Invalid metadata is treated as unknown rather than ignored.

Recovery must include actual handle inspection and a reason. A held lock or observed live process group always refuses recovery, even with `recover <task> --reason ... --stopped-check`. A recorded group that is absent can be reconciled by eligible recovery, or a fresh verification can supersede it. Documentation, review and completion refuse unresolved attempts. Failed ownership/status validation never rewrites crash evidence. Eligible recovery persists its stopped observation before changing ownership in the database: a metadata write failure leaves ownership unchanged, while a later database rollback leaves a valid stopped observation and allows recovery retry. The reconciled attempt state records an observation, not a claim that reassignment succeeded. An unresolved unknown launch requires the explicit `--stopped-check` acknowledgement and a substantive reason (at least 20 characters) after the operator has inspected the actual local/external handles. This acknowledgement is recorded privately; its truth is a host responsibility. Recovery does not kill, restart or wait for workers. An owner release cannot bypass unresolved unknown state; use inspected recovery after lease expiry when needed.

Ordinary completion and timeout retain bounded process-group cleanup, including same-group descendants; check launch errors produce failed results. Catchable interruption attempts normal cleanup while retaining conservative attempt state if observation or persistence failed. A hard kill cannot run cleanup. Once handles are actually stopped, retry verification or perform explicit inspected recovery. Never delete lock files as recovery: replacing their inode defeats coordination.

Heartbeat authenticates the active task token and renews its lease even if it expired, provided ownership has not changed. It reports an execution-eligibility/drift indicator independently of input freshness, so an owner reconciling changed sources can remain present. This is a genuine caller activity report, not a background assertion of life. Verification and completion remain freshness gated. Long checks renew the same active owner before attaching their result; final token and freshness validation still apply. Lost ownership cannot attach a receipt. Check/documentation/review acceptance gates remain unchanged.

These guarantees apply to cooperating local POSIX controllers sharing the same workspace and lock inode. They do not secure malicious code, edited/deleted state, detached or remote descendants, changed sessions, PID/process-group reuse, reboot persistence semantics, or distributed filesystem locking. A reused group identifier or unreaped zombie may conservatively block recovery; inspect it rather than inferring death from elapsed time. A check can detach beyond its original group; the controller cannot prove all such activity ended. No process start-time identity or distributed liveness guarantee is claimed.

The recovery regression suite uses real subprocess overlap and a killed fixture controller with a surviving child. Only owned temporary fixture processes are killed. It also covers explicit unknown-launch reconciliation, timeout/launch errors, interruption, read-only status, unreadable metadata, metadata/database recovery failures, stale-input heartbeat and old-token result fencing. The unobserved spawn/persistence interval is modeled conservatively; tests do not claim exhaustive OS crash or malicious-process coverage.


## Bounded capture operations

Tasks opting into bounded-v1 capture use concurrent nonblocking pipe reads and an aggregate raw-byte budget. Already captured timeout diagnostics remain private previews/base64 evidence. On limit,timeout or capture fault the owned group is killed and cleanup drains/observes for at most2application seconds; descriptors then close. Blocking spawn/uninterruptible OS operations, detached/remote descendants and malicious operators are outside that timer/sandbox guarantee. If direct-child reaping, stream EOF or group absence cannot be established, CaptureUncertain leaves conservative attempt metadata and no accepted result. Inspect actual handles before recovery; a quiet pipe or expired lease is not process termination.

Catchable interruption and durable-start callback failures attempt the same cleanup and propagate; hard kills cannot guarantee cleanup. `record(stopped)` occurs only after a normal helper return; accepted metadata becomes completed only after guarded publication. An older PASS cannot bypass an unresolved new attempt. State guards remain local cooperation, not process-start identity or distributed liveness proof.
