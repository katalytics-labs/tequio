# Tequio 0.19.0

## Understand the decisions you are building

`$tequio-explain` is an optional way to learn about a project decision. Ask for a topic such as load balancing, a backend design or a deployment tradeoff. The agent reads the relevant context, distinguishes current implementation from proposals, and creates a standalone offline lesson.

Lessons combine readable explanations, causal visuals and useful interaction. The portable example follows requests through routing, queues and processing, with guided overload and server-failure scenarios, pause, step and replay. Authors adapt the example to the topic; unrelated subjects do not inherit routing controls. Prediction and a different transfer case help the reader test their reasoning without a compulsory quiz or mastery claim.

Preparation is temporary first. Explain then asks where to keep the material, or uses a destination already supplied. A folder outside the repository can be its final home. Copies are verified before disposable staging is cleaned; collisions and uncertain cleanup preserve existing content and are reported. Vault storage does not imply JavaScript runs inside a note viewer: open the HTML in a normal browser. See [the artifact and delivery contract](../explain-artifacts.md).

`$tequio-learn` keeps its existing role: codifying demonstrated project findings into maintained guidance. The four everyday development phases are unchanged. There is no new runtime service, required learning phase or package dependency.

## Keep testing useful as a project grows

Tasks, Build and Check now share [proportionate testing guidance](../../skills/tequio-check/references/proportionate-testing.md). Start development feedback with relevant checks, then justify final coverage using changed behavior, dependencies, risk and project rules. Broader suites remain appropriate when required or when impact is unclear.

This guidance does not skip declared checks or weaken freshness, documentation and independent review. Maintenance is bounded by actual friction or relevant edits, preserving distinct regression and security coverage. Removing or quarantining a failing test cannot turn a missing acceptance check into a pass. No automatic test selector, new schema or mandatory suite audit is introduced.

## Compatibility and limits

The project-local clone-and-install workflow is unchanged. Updating an existing project uses the documented [update procedure](../../README.md#update-or-uninstall); unchanged installer-owned assets are refreshed while modified owned assets cause a refusal. New lessons belong outside installer-owned assets. No global configuration or other project is upgraded automatically.

Runtime requirements remain Python 3.11+ and POSIX locking/process support. Native Windows remains unsupported; WSL 2 remains an experimental route. The lesson example uses bounded local JavaScript and no remote assets. Reduced motion, readable scriptless states and print reasoning are provided; narrow screens use a scrollable diagram with stacked text. A browser is needed for interactive playback.

Qualification covers the actual finite model, default/prefixed installation and lesson preservation, a generated synthetic project lesson, browser controls and rendered alternatives, plus synthetic vault-style copy/failure cases. These observations do not establish physical-device or actual Obsidian execution, learning mastery, universal agent compliance or secure arbitrary generated HTML. The CLI records evidence and guards its transitions; agents must still inspect what they generate. See [validation](../validation.md) and [compatibility](../compatibility.md).
