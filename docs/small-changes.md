# Small changes in an existing project

Use the same four phases for a bug or bounded feature. The artifacts describe the change and its preserved contracts; their size follows the uncertainty and risk of that change. There is no separate small-change command or bypass mode.

1. **Explore:** read repository guidance, affected code, tests and current docs. Capture the symptom/request, reproducer, expected behavior and exclusions in the brief. Write focused nonempty analysis and spec files with source references, observed versus suspected causes, changed contract, preserved invariants and acceptance/failure cases. Record analysis normally.
2. **Design:** write one focused plan if one is enough. Map each requirement to the correction, affected paths, checks, documentation impact and integration owner. Reuse existing architecture; explain material changes. Record the normal plan receipt. Wider discoveries require affected inputs to be reconciled before proceeding.
3. **Tasks:** import one complete task when appropriate. Its workspace-relative `sources` reference actual brief/analysis/spec/plan files. Declare concrete read/write prefixes, observable acceptance, executable argv checks, risk, dependencies and documentation impact. Complete routine agent-owned specification choices for every agreed task; a ready starter is not enough if the rest can be specified. Genuine unresolved decisions remain draft with a sourced reason and concrete resolution action under the [task-review contract](task-review.md). Dependency waiting alone does not imply draft. Keep excluded work explicit rather than generating a whole-product backlog. Reuse relevant qualified specialists; no extra specialist is required solely because a change exists.
4. **Build:** claim the task, keep the token private and heartbeat active work. Reproduce the baseline, make the owned correction, run regression and nearby/integration checks, and update affected maintained docs. Record a source-by-source documentation reconciliation after current verification. Obtain a distinct real correctness review (and security review when risk requires it). Complete only with fresh accepted evidence; checkpoint with review pending if no independent reviewer is available.

A small scope does not waive ownership, nonempty source artifacts, acceptance, documentation, verification or independent review. Task declarations coordinate ownership; they do not sandbox writes. If the fix expands beyond ownership or changes the agreed contract, replan affected work. Existing global/shared requirements still apply. Record actual baseline failures and unrun checks honestly.

See [the existing-project exercise](../examples/existing-project/README.md). Its deterministic prewritten correction demonstrates controller mechanics and real Python tests. It is not evidence that a model diagnosed the bug, delegated work, reviewed independently or improved productivity.

## Prefer the next useful product slice

Use a small experiment only when a concrete uncertainty blocks product implementation. The optional installed experiment template captures reuse, minimum positive/adverse observations, actual effects, ceilings, stop classification and decision/next slice. Put faithful cheap parser/import/context checks before costly integration. Missing tools/input or exhausted resources remain unqualified; a coding defect calls for correction, not a claim that a technology is unsuitable. Prefer tests against the actual product path over a second application.

A synthetic adapter exercise in tests/test_proportional_flow.py demonstrates this ordering: a fresh Python child imports the temporary product module and checks its parser and selected multiprocessing context before a local effect sentinel runs. It does not launch a multiprocessing worker or prove host-agent judgment. Correcting the adapter permits one actual local integration effect; adverse input is rejected. Complete observations can rule out a bounded unchanged API requirement; missing input/budget never supplies that decision.

Distinguish development feedback, focused correction rechecks, stable independent acceptance and final combined proof. Material authorization/interface/configuration changes need current affected checks/docs and required actual reviews; a feedback file alone cannot close a task. Use [reviewed revision](revision.md) for a selected unfinished refinement, or deliberate broad replan for a broad change. [Policy boundaries](policy-boundaries.md) demonstrates smaller churn without weakening freshness. Report usable outcome, open acceptance and next concrete value; reassess at the declared time/correction ceiling with billing unknown when unavailable.
