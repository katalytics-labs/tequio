# Checkpoint and resume context

`checkpoint` explicitly writes schema version 1 with current status, project/input hashes and a run-context observation. `resume` is read-only: it reports healthy current status even when checkpoint JSON is truncated, null, a nonobject, missing required fields, or has an unsupported version. `checkpoint_issue.code` identifies the problem; unknowable change flags are JSON null. Damaged bytes remain untouched. Only an explicit checkpoint overwrites them. This does not repair state or recover claims.

`context.policy` reports `valid`, `invalid`, `missing` or `unreadable` plus a digest, never policy prose or permissions. Validation requires mode next-chunk/backlog, a nonempty scope string, unique nonempty string task IDs (nonempty for backlog), a string/null integration branch, boolean local commit/merge/push flags, and a positive integer writer cap. This is structural validation, not authorization or approval of those task IDs. Unrecognized fields are retained only through their digest. The digest hashes complete parsed canonical JSON, including private notes and unknown fields, so whitespace/key-order changes do not count; array order and prose edits do. Invalid JSON is hashed as bytes; missing/unreadable policy has no digest. Missing and invalid states remain distinct. Hashes are observations, not confidentiality against guessing known content.

`context.task_scope_digest` hashes all stored task definitions ordered by task ID, including IDs, scope, exclusions, sources, checks and other immutable definition fields. It excludes exactly `freshness.RUNTIME_FIELDS` (inputs, specialist bindings, documentation baseline/receipt and result hashes/snapshots). It uses recorded definitions, not task-import file bytes. Importing a new task changes scope. Claim/heartbeat/status progress does not. `progress_digest` separately hashes task ID/status pairs; `task_progress_changed` compares that digest independently of task scope; it is an orientation aid rather than a full event, ownership or evidence history.

`policy_changed` compares policy state/digest, and `task_scope_changed` compares the recorded-definition digest. These are independent of `project_changed` and `inputs_changed`. Unchanged missing/invalid policy can compare equal without becoming valid authorization. Valid legacy checkpoints without a version still supply project/input comparisons, with `legacy-context-unknown`, `context_unknown: true` and null policy/scope/progress changes. Unusable versioned context returns unknown drift and an issue instead of false assurances. No automatic migration or policy mutation occurs.

Before continuing, reconcile current policy and task scope against persistent and current user instructions. Current authorization governs; an old or new hash grants nothing. Follow already explicit authorization without routine permission requests, and resolve real scope/permission gaps before dependent work. Inspect actual files, receipts and live handles as before. Snapshot reads are sequential observations, not a transaction spanning files, policy and task state; concurrent changes can require another read. Resume adds no scheduler, process kill, state repair, Git operation or lifecycle acceptance bypass.

Policy reads follow ordinary filesystem symlinks. The resulting state/digest is a private observation; no target contents or raw policy prose are exported by this observation. These helpers do not create directories or replace policy files.

## Optional execution checkpoints

A policy may include `execution_checkpoints` with exactly `version: 1`, positive integer `wall_minutes` and positive integer `max_verifications_per_task`. Booleans, floats, zero/negative values, unknown versions and extra keys invalidate the supplied policy. Omission preserves legacy structural validation; progress labels it `legacy-unbudgeted` rather than interpreting it as unlimited spending. Unknown other policy fields remain private and digest-bound as before. No existing task/checkpoint is rewritten or lifecycle acceptance weakened.

The template suggests a30-minute/three-published-verification checkpoint; these values guide the host, do not measure model usage or authorize continuation. See [execution efficiency](execution-efficiency.md) for observations, corrupt/unknown time, progression and bounded rollout.


## Opt-in compact pickup

`resume --summary` delivers version1 fixed context without duplicated saved/current task arrays or saved prose. Default CLI/Workspace.resume output remains unchanged. The compact object includes workflow reason codes, lifecycle counts, changed/unknown flags, context digests, checkpoint issue/reference, optional next-task focus, active count/first3items/omitted count, checkpoint advice with first3reasons/omissions and unknown usage. Normal long-prose/many-history fixtures stay below8KiB; this is delivery volume, not parsing-memory/cost measurement.

A no-follow regular checkpoint acquisition happens before Status/progress; the same immutable bytes are injected through private clock helpers and hashed for the reference. Replacement cannot bind a later file to earlier parsed content or follow an external symlink indirectly. Unsafe/missing/unreadable/invalid/legacy/unsupported context remains explicit; no authority or liveness is inferred. Malformed projected enums/IDs become invalid/unknown, not raw private text. Existing-workspace summary preserves sequential-observation limits. Missing workspace in summary mode returns existing intake/selection guidance without creating state; default resume still refuses it. Git lanes read the original controller. Summary is private operator metadata, not a public export or execution authorization.

Compact acquisition pins no-follow directory descriptors from the canonical project anchor. If the workspace parent is unsafe, it returns unavailable context without inspecting aliased current state; active count/omissions are null because they are unknown, not zero. This does not alter the default full-resume parser.

## Effective revision context

Immutable definition identity is insufficient to describe a rebound consumer. Current run context also accounts for revision effective dependency/input bindings separately from stored definition bytes; a rebinding must be reconciled even when the original task body is unchanged. Inspect the [revision intent/application](revision.md), current proof and affected descendants on pickup. An applied digest is historical operation evidence, not current acceptance or permission. No-overlay context retains existing behavior. Saved summaries, task counts and matching policy hashes cannot bless stale checks or completed historical dependencies.

## Optional model policy and routing toggle

A supplied `model_delegation` block is validated with exact version1 keys, including boolean enabled; absent block preserves legacy behavior. Disabled still validates completely. Malformed/null/unsupported supplied data makes the whole policy observation invalid; unrelated top-level fields and the existing complete-JSON digest remain unchanged. Canonical key-order/whitespace equivalence remains; semantic on/off changes affect policy digest and checkpoint `policy_changed`. No context envelope/schema/database migration or automatic checkpoint repair is added.

[Model delegation](model-delegation.md) and the payload-resident [Routing contract](../skills/tequio-routing/SKILL.md) specify caps, safe control/status behavior and private provenance. CLI configuration validity and drift observations do not authorize work, select models, authenticate identity or enforce host-required diversity. Existing policy/read observers retain their documented behavior; the new routing command's bounded no-follow IO is not a whole-policy parser migration.
