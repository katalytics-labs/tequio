# Security assessment and integrated release review

Every ready task declares `security_assessment: {"surfaces": [], "reason": "Concrete explanation of the affected boundaries"}`. The trimmed reason must contain at least 30 characters. Surfaces are unique values from: `authorization`, `authentication`, `secrets`, `personal-data`, `data-export`, `untrusted-input`, `code-execution`, `dependencies`, `configuration`, `network`, `storage`. Use the categories by meaning, not filename heuristics. Explain an empty list; it is an assessment, not proof of safety. Drafts may omit the object, but supplied malformed assessments (including null) fail import.

`risk` remains the review classifier: `normal` requires correctness review; `security` also requires independent adversarial security review. Any nonempty surface list requires `risk: security`. A conservative security task may have empty surfaces. Reviewers challenge the assessment against actual sources and changes. Correctness and security reviewers must have distinct IDs and differ from the owner. IDs are local assertions, not authenticated identity or proof of independence.

## Integrated releases

Use `kind: release` for an integrated candidate; other kinds remain `implementation` (default) and `research`. Release always requires security risk. Research-only specialists cannot execute releases. Reuse qualified project-owned specialists through the specialist factory when expertise is needed; Tequio supplies no generic stack specialist catalog or security scanner.

Declare nonempty `candidate_paths`, concrete project-relative files/directories covered by task `reads` or `writes`. Project root, reserved toolkit/VCS path components, globs, traversal and symbolic links are rejected. Declare the full intended candidate, lockfiles, configuration and relevant export context through resources. Candidate content is explicitly included in global and scoped snapshots, including files normally excluded from the global project hash. The candidate may be absent during planning/claim so the owner can assemble it; it must exist for verification, review and closure. Directory hashing rejects nested symlinks. Review declared scope and completeness; the runtime cannot identify omitted files semantically.

The security review report for a release is a workspace-relative JSON file. It uses the existing review receipt, report hash and task snapshot; there is no additional approval ledger. Its shape is illustrated by `../../../templates/release-security-report.json`: exact ordered `candidate_paths`, a `coverage` object with exactly `candidate-inventory`, `dependencies`, `configuration`, and `privacy-export`, and an explicit `gaps` string list. Each area declares `disposition: reviewed` or `not-applicable`, a concrete reason of at least 30 trimmed characters and an `evidence` path list. Reviewed areas require evidence; candidate inventory cannot be not-applicable. Evidence must exist within declared project read/write resources. Record actual unresolved issues through review findings as well as explaining gaps; the runtime validates structure, not semantic accuracy, report completeness or reviewer expertise.

Inspect actual dependency manifests/locks and dependency risks, configuration defaults and deployment assumptions, secrets/personal data and public/private export boundaries. Include concrete checks, findings, coverage limitations and why any area is not applicable. Do not copy secrets into reports or logs. A substantive report must also meet the ordinary review length requirement. Changes to bound content invalidate checks/docs/reviews; changing the report invalidates its hash. Obtain fresh evidence after changes.

Authoritative candidate paths currently must be inside the controlled project. For an external export, first review the assembled project-side candidate, then copy it to the authorized destination and compare exact content/digests, retaining private provenance. That copy comparison is a host procedure, not an external-output gate enforced by this runtime. A receipt does not authorize publishing, deploying or sending a candidate and is not security certification.

## Existing workspaces and migration

Unfinished tasks with missing or invalid assessments are explicitly `migration-required` in status/proof and cannot dispatch, verify, record documentation/review or complete. Preserve live work and inspect actual owners/processes. Heartbeat, release, recovery, checkpoint and read-only diagnosis remain available; heartbeat reports execution drift. Release active ownership deliberately, refresh analysis/plan through replan and import replacement immutable task IDs with explicit assessment. Do not patch stored task bodies or silently assign safe classifications. Existing completed/superseded records remain historical and readable; their closure is not qualification under this contract. Existing integration and verification recovery gates remain in force.
