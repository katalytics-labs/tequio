# Tequio Build

## Runtime and context

Use `python3 bin/tequio --project <absolute-project> --workspace <name> ...`. Select workspace explicitly from the user's task or the default `main`; never pick by modification time. Installed instructions/assets are under `.tequio/`. Read `.tequio/roles/orchestrator.md` and only relevant specialist skills. User/host instructions govern; this toolkit does not override authorization or grant tools. Keep task tokens, evidence, prompts and working notes private. Do not print secrets in summaries.

## Procedure

Run `resume`/`status`, inspect actual project state and any real live agent/process handles. Default one ready task; a user-requested batch may run a bounded set of independent tasks up to host and task-engine capacity. A stale plan or blocked dependency is not permission to skip it. Claim with `claim --owner <agent-id>`; save the returned token privately. Each writer agent claims its own task or receives its explicit claim/token privately. Never create fake native agent types; compose available delegation with role and specialist instructions.

Read the full returned task, source sections, current code and relevant specialist skills, not just the title. Assign disjoint resource ownership; serialize shared contracts and integrate under one owner. No Git writes/publication unless authorized. Preserve source requirements and do the complete bounded outcome, including real wiring, meaningful tests and relevant architecture documentation. Keep existing unrelated work intact. Heartbeat long-lived claims; release with a reason if stopping, or `release --blocked` with an actual resumption condition. Lease expiry alone does not prove an agent is dead.

## Documentation is part of the chunk

While implementing, reconcile the brief/spec/plan, the exact todo scope and actual current code/tests. Keep relevant product docs current as behavior settles: interfaces/errors, data and state rules, access boundaries, setup/operation and failure/recovery as applicable. Describe observed implemented behavior, not unbuilt plan promises. Keep future/partial scope explicit; triage disagreements into a reviewed decision/replan rather than silently rewriting the plan to fit accidental implementation. Do not publish private analysis, prompts, transcripts or agent chatter as product docs.

Task `documentation` declares update paths within write ownership, or an explicit `not-needed` rationale subject to correctness review. Update declared files as part of the implementation, not a separate later documentation phase. Generic coordinator/check-only work may justify no product-doc change; this is not an automatic bypass for code changes. If docs impact wasn't planned, revise the task before claiming rather than editing unowned shared docs.

Run `verify <id> --token <token> --summary` against actual task checks. Fix failures within scope; if scope/requirements change, stop and replan affected work. Check receipts are conservative project-content snapshots: concurrent changes can invalidate them, so integrate then re-run only when needed. A successful verify moves to review. Write a private reconciliation JSON from `.tequio/templates/documentation-report.json`, covering every exact source in the task, with actual project-file references and all declared doc paths. `outside-this-task` distinguishes broader planned scope; unresolved deviations require triage/replan. Record it with internal `record-docs <id> --token <token> --report <workspace-relative-json>`. No separate document skill is needed. The receipt requires actual changed documentation (or declared no-change rationale), fresh successful checks and source coverage; it does not prove semantic accuracy. This invalidates older review so the current reconciliation is reviewed.

Use a distinct correctness reviewer, plus adversarial security reviewer for security risk, with task/context/output/evidence. Read delivered reports; failed/empty/timed-out reports are not clean. Reviewers return substantive report paths and unresolved findings. The orchestrator records `review` with the actual reviewer ID/kind/report and each finding. The CLI checks identity strings, not cryptographic independence; do not fabricate a second actor.

Resolve findings, re-run relevant checks and obtain fresh review. `complete --summary ...` only after criteria, integration, current documentation reconciliation and evidence are satisfied. The CLI refuses closure without a fresh docs receipt and matching correctness review; changed behavior/documents/report require refreshed evidence. Scope/resource policy requires agent compliance and review; CLI does not sandbox arbitrary edits. Write `checkpoint --summary ... --next ...` and return the chunk result, tests, limitations and next task. Default to one chunk. Continue through later waves only under an explicit bounded backlog run policy; revalidate each wave before dispatch. At a milestone boundary, review combined outcomes and refresh provisional future tasks before continuing.

If independent review cannot be performed, retain review-pending state and explain the missing evidence. Do not impersonate a reviewer to bypass closure.

## Proportionate execution and checkpoints

Before prolonged/autonomous work, declare a concrete time checkpoint and a repeated-correction/review threshold in private run-policy, using optional `execution_checkpoints` (version1, wall_minutes, max_verifications_per_task). Template limits are starting checkpoints, not owner-approved unlimited spending. If no meaningful token/cost limit or telemetry is available, say so, work one bounded chunk and report before extending. Missing legacy limits never mean unlimited autonomy. At a due checkpoint, report acceptance still open, useful results, current findings, elapsed wall time, observed usage/source or unknown, and the next coherent proposal. Elapsed time or silence is not owner approval. Inspect internal `progress [TASK]` for CLI-published counts/time advice; these are neither all host activity nor current acceptance. Do not use another checkpoint to hide accumulated failed/correction cycles.

Separate three activities: development feedback helps shape incomplete work; focused rechecks assess a specific correction and its material impact; final independent correctness/security reviews assess the actual stable candidate, current checks and docs. Use early review when risk justifies it, not as a mandatory full dual-review lifecycle after every intermediate edit. Do not register a partial/source-only review as final acceptance. Give final reviewers compact source refs, exact delta, check/receipt refs, remaining findings and coverage limits. After material corrections, refresh affected evidence under existing freshness rules and obtain the required current reviews; do not repeatedly replay unrelated history or invent independence.

Prepare a coherent candidate and maintained docs/config/check inputs before authoritative verification and costly external effects. Use cheap local checks for development. Execute an expensive live check only when its prerequisites, source and authorization/resource budget are stable; preserve its actual-current-behavior requirement. Record documentation reconciliation after successful verification and final reviews against that same content. Do not change bound docs afterward merely to summarize progress: private journal/review reports can hold progress notes. A material bound contract/doc/source change still invalidates evidence as before. Never silently replay mail or other external effects, exempt Markdown, parse a previous PASS instead of executing behavior, or retrofit stored checks to avoid reruns. Use existing reviewed scoped-v1 only when its full dependency boundary can be justified; otherwise retain conservative global verification. An invalidated costly check needs a deliberate current revalidation decision within existing authorization, not automatic reuse.

## Check runner and compact coordination

When the intended runner changed or a material capability is known to be restricted, inspect the declared checks' actual prerequisites before expensive execution. Use a cheap faithful probe only where justified (for example, whether process inspection is permitted for process-cleanup tests), not a new mandatory preflight framework. If a worker cannot execute required checks, use an already-authorized capable runner and record executor/environment provenance and cumulative attempts; if none is available, retain acceptance pending with the precise gap. Do not widen permissions, change models, skip tests or substitute a prior PASS automatically. A probe is not acceptance evidence for the full check.

For substantial reusable instructions, focused applicability/source-boundary feedback before the full suite can catch defects cheaply. This is optional development feedback, not another mandatory dual-review cycle; final actual independent reviews still inspect stable content and current evidence. Stabilize release metadata before combined proof only when release work is already authorized; later authorization and changed bytes may legitimately need new proof.

Prefer targeted source/delta reads and concise worker handoffs. Wait on real process handles at meaningful intervals while remaining responsive to owner messages, leases and checkpoints; avoid repeatedly replaying unchanged logs. Unknown usage remains unknown. These practices remove coordination repetition, not verification or review obligations.

## Proportionate testing

Use nearest meaningful behaviour/dependency/failure-path checks while iterating, broadening for shared or uncertain boundaries. Final verification still runs every declared mandatory command with current docs and actual applicable independent review. See [proportionate testing](../tequio-check/references/proportionate-testing.md) for selection and bounded maintenance; imported check-contract changes require supported reviewed revision/replan, never historical edits.

## Bounded existing-project execution

For a small fix, follow the same claim, verification, documentation and independent-review gates with focused inputs. Reproduce the reported failure before editing when feasible, then implement the smallest complete correction within owned resources. Run the regression and appropriate nearby/integration checks; report which actually ran and any baseline failures. Preserve unrelated behavior and existing architecture unless the source-linked task explicitly changes them.

Reconcile only the agreed delta and its preserved contracts; do not regenerate whole-product documents to make a one-task fix look complete. Update the affected maintained documentation, or use the task's reviewed explicit no-change rationale. If the actual fix exceeds ownership or changes the acceptance contract, stop and replan affected work. A deterministic fixture or prewritten patch is a reproducibility check, not evidence of model discovery, independent review or productivity. Leave review pending if a real distinct reviewer is unavailable.

## Optional Git lanes

Status reports existing repository and isolation configuration. Default to shared-folder coordination; when a repository exists, offer optional worktree isolation and respect the user's choice. Never initialize a repository to enable this feature. After explicit opt-in, use internal `git configure worktrees` and `git lane <lane-name>` for independent writing lanes, not every read-only reviewer. Consult the Git isolation guide in the source distribution and CLI help for prerequisites and recovery limits. Git helpers do not replace claims, resource declarations or review. Keep lifecycle commands anchored with `--project <original-control-root>`; never create a separate task database in a lane. Check lane files within the lane, then integrate under one owner, re-run authoritative verification and obtain fresh documentation/review receipts. The lane helper itself does not commit or merge. The host orchestrator may use native Git for local commits and integration only under the agreed run policy below. Cleanup, pushes and publication require their own authorization. Shared mode remains fully supported.

## Execution mode and integration ownership

The user may choose next-chunk mode or authorize an autonomous run of an agreed backlog/milestone. Record the choice privately in the selected workspace's `run-policy.json`, starting from `.tequio/templates/run-policy.json`; do not treat the template default or the mere existence of a Git repository as commit/merge authorization. Resolve scope to task IDs, maximum parallel writers, the integration branch, and whether local commits/merges are allowed. Respect persistent user authorization; do not ask again for every authorized commit. A bare build request follows the established policy, defaulting to next-chunk if none exists. This policy guides the host agent; it is not CLI-enforced authorization or a background scheduler.

In backlog mode, the host orchestrator repeatedly selects ready work, dispatches bounded writers, obtains actual independent review, integrates, verifies and checkpoints, until the approved scope is complete or a real stop condition applies. Workers may make local lane commits when authorized, staging only explicit task-owned paths after inspecting the diff and excluding private material; never use blanket staging. Keep task IDs in commit messages. Use existing Git identity; if it is missing, report the blocker rather than inventing identity or changing global config.

The orchestrator is the sole integration owner. Inspect each proposed commit and review against the task before merging; keep integration serial on the agreed branch. Before every merge inspect branch/HEAD, clean index/worktree and in-progress Git operations, preserve unrelated user changes, and confirm the lane commit and resource scope. Use ordinary local Git without force/reset or implicit publication. Resolve conflicts only within the authorized scope and competence, then refresh review; otherwise preserve the conflict state and checkpoint a precise blocker. Check the combined result and refresh authoritative verification, documentation reconciliation and independent review before closure. A lane commit is not task completion, and a successful merge is not acceptance.

Continue with the next ready tasks without requesting routine permission inside the agreed policy. Do not expand scope, weaken checks, fabricate reviewers or call an incomplete product finished to keep the run moving. At host/session limits write a durable checkpoint with active owners, lane/branch/commit references, current findings and next step. Resumption still requires the host to run another turn/session; Tequio cannot keep a stopped host alive. Report completed tasks and remaining blockers against the approved milestone, never infer whole-product readiness merely from an empty task queue.

## Run-context reconciliation

Checkpoint version 1 records policy validity/digest and recorded task definitions separately from progress. On pickup/build, inspect `policy_changed`, `task_scope_changed`, `context_unknown` and `checkpoint_issue`, plus current private run policy and approved task IDs. Reconcile changed or unknown context against persistent/current user authorization before dependent continuation; current user instructions remain authoritative and a digest never grants permission. Continue already explicitly authorized work without routine permission requests. Missing/invalid policy is not an approved backlog. Legacy or damaged checkpoints require orientation from healthy current status, files, receipts and actual live handles; resume preserves bytes and makes no repair. At handoff explicitly checkpoint the reconciled context and describe unresolved scope/authorization gaps privately. See `docs/run-context.md` for hash boundaries and limits.


## Exact-commit integration recovery

When using registered Git lanes, the integration owner pins the selected full commit SHA with internal `integration plan TASK --token TOKEN --lane NAME --commit FULL_SHA --branch BRANCH` from the original controller and explicit workspace before native integration. Follow `docs/integration-journal.md` for identity, scope and recovery constraints. The journal observes Git and never performs or authorizes a merge. Resume the immutable intent; do not substitute a moved branch tip or infer squash/cherry-pick equivalence.

Inspect `integration status TASK` after interruption. If exact SHA is integrated but unrecorded, run `integration reconcile TASK` before authoritative verification. Preserve dirty/conflicted/mismatched/rewritten state and inspect the blocker. A new owner authenticates the identical plan retry before continuation. After durable integration/reconfirmation, obtain genuinely new current checks, documentation reconciliation and required independent reviews; readiness is not lifecycle completion. Status/history never authorize work or certify semantic coverage. Journal-free shared-folder work remains supported.

## Security workflow

Before execution, inspect the task security assessment and affected boundaries. For release work, build the declared project-side candidate before verification and obtain current structured security coverage. Read [security workflow](../tequio-tasks/references/security-workflow.md) for candidate binding and migration constraints.

Use the compact response for routine delivery; inspect the exact private receipt path/hash for acceptance evidence and relevant failed-check details. The summary omits raw commands/output/errors, caps diagnostic items at three and reports omissions. It does not truncate stored evidence, certify privacy/publication or replace actual review. Default CLI JSON and direct verify API remain available unchanged. Refusal/infrastructure errors produce no summary and must not be replaced with an older PASS.


Use Status `checks.state` to distinguish current evidence from missing/failed/stale/invalid/unavailable verification. `verification-required` means finish outstanding implementation and documentation edits, then verify a stable candidate before recording reconciliation or requesting independent review. Editing docs and recording their reconciliation are different steps; do not reverify automatically on every stale observation. Live-operation, migration, phase and integration reconciliation retain priority. Status itself executes nothing.

Draft `draft_readiness` shows only structural state/category. Inspect the named task's existing sourced resolution action privately before asking an owner question; a recorded category is not proof that owner input is necessary. Legacy/invalid metadata stays unknown, ready dependency waiting remains ready, and no extra draft paperwork is required. Done/superseded checks are not-observed rather than requalified by a status read.

For routine pickup use internal `resume --summary`, retaining full default resume for targeted private inspection. The compact response preserves changed/unknown policy,scope,progress/project flags, same-read checkpoint reference and bounded active-operation observations/omissions; it is not permission to resume/recover. Inspect omitted/unknown work and original evidence before acting, never guess by recency.


New task/release templates declare `capture:{version:1,mode:bounded-v1,max_bytes:1048576}`: one retained raw-byte budget across stdout/stderr and all checks. Existing tasks without this field keep legacy behavior; never retrofit imported definitions. Consider output volume and actual effects while authoring; supplied limits must be integers1..16777216. Limit/timeout/capture failure retains a bounded private prefix and fails rather than accepting truncated evidence. Use supported replan when a policy truly needs changing; no automatic retries of expensive effects or old-PASS reuse.

Bounded receipts/summaries use version2 with attempted versus actually executed counts and explicit skipped checks. Failed launch is an attempt, not an executed child or skipped check. Inspect exact private receipt evidence on failure; raw/base64 output never belongs in compact delivery. Unknown cleanup requires actual handle inspection, not inferred process death. Capture policy does not grant command authorization or automatically classify every project task as security-sensitive.

## Product feedback and stable acceptance

When a genuine uncertainty blocks implementation, reuse current code/evidence and the optional experiment record before creating another harness. Run cheap faithful product-boundary checks before expensive integration; a failed prerequisite stops dependent effects. Record enough positive/adverse observations for a bounded supported/unsuitable decision; missing input/budget stays unqualified. Carry the decision into a concrete product slice.

Use developer feedback and focused finding rechecks during edits, then obtain genuine required independent correctness/security reviews of the stable current candidate. Do not default to full dual review after every intermediate correction. Material authorization/privacy/interface/process/configuration changes require current affected checks/docs/review; never reuse old PASS or waive final combined proof. Finish with usable outcome, exact evidence, open acceptance, cumulative checkpoint/correction observations, unknown billing and next useful value. Consult Redirect for explicit reviewed revision instead of editing stored definitions.

## Optional model-delegation policy

Before useful delegation, read the complete installed `.tequio/skills/tequio-routing/SKILL.md` contract and actual workspace policy. Use scripts first for deterministic work; assess uncertainty, consequences and checkability. Choose only authorized available host options; pinned models/budgets outrank preferences. Do not escalate to costlier choices or retry quota indefinitely. Keep requested versus actual observed identity/source/fallback honest in an optional private delegation-record for meaningful decisions. Required unknown diversity remains host review-pending; the CLI neither dispatches/authenticates models nor enforces that instruction. Explicit owner off suspends only this optional policy, never mandatory current checks/docs/independent actors or higher-priority rules.

## Stale completed prerequisites

Completed evidence can become stale after a legitimate read-context change even when owned outputs and task inputs match. Inspect the named causal prerequisite from Status/claim. Preserve old completion/receipts; use ordinary reviewed fresh successor tasks covering the stale chain, then a reviewed rebind-only revision for the unfinished consumer. No old-PASS reuse, implicit aliases or historical body resets. New successors require fresh checks/docs and actual applicable independent reviews; subsequent drift blocks again. Changed outputs/requirements need actual successor correction/acceptance, not a context-only waiver. Source checkout details: `docs/prerequisite-recovery.md`; standalone projects use the successor import/lifecycle and rebind commands in Tasks. Historical unrelated specialists are not live revision work, but specialist freshness still applies to new/unfinished dispatched work.
