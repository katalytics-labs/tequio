# Tequio Explain

An optional teaching entry point, outside the four development phases. `$tequio-learn` still codifies demonstrated project learning into maintained guidance; Explain teaches the person. Neither reading nor answering a lesson approves a design or resumes development.

## Select the question

Use an explicit topic. For bare invocation infer only one unambiguous topic from immediate discussion or an explicitly named current decision, and state that assumption. If multiple topics fit, ask one short topic question; do not scan the entire project or guess a workspace by recency. No project is required: a general example must be labeled hypothetical. Use supplied depth, otherwise novice-friendly core with optional depth. Bound broad topics to a small relevant map and one useful mechanism; do not impose questionnaires, courses or mandatory quizzes.

Read the minimum relevant current project source and accepted/proposed decisions. Respect active ownership; half-integrated files are not authoritative. Distinguish implemented, accepted, proposed, hypothetical and unsupported claims. Challenge unnecessary complexity rather than teaching a proposal as inevitable. Cite repository-relative files/symbols, inspected revision/date when known, and current applicable primary references for time-sensitive service/security claims. If browsing or sources are unavailable, preserve that uncertainty and narrow the claim. Research queries must not disclose private source, secrets or diagrams. Host/provider handling still applies: do not promise all processing stays local.

## Prepare a useful lesson

Read [the teaching and delivery contract](references/teaching-artifacts.md). Start from [the portable shell](templates/lesson.html), retaining its safety/accessibility affordances while replacing the example with the actual topic. It is a complete **synthetic routing example**, not a universal simulation or already grounded project lesson. Do not deliver it unchanged as an explanation of an unrelated topic. For a backend design, a worked state transition/storyboard can be better than routing controls. Remove misleading irrelevant controls.

Prepare in a new private temporary directory first, normally outside the repository. If using `.tequio/learning/`, verify tracking/ignore and ownership before writing; ignore is not secrecy. Never place a lesson in installer-owned skills/runtime or authoritative briefs/analysis/specs/plans. Include overview, objective/assumptions, project relevance/status, a worked example and actual causal visual. Use restrained cohesive typography, strong hierarchy, readable spacing and meaningful animation—not decorative dashboards. A control must change the explained shared model and visible reasoning. Invite prediction → observation → explanation, then a novel transfer case with separately revealed reasoning. Optional native details hold depth; core content remains visible. Understanding is an objective, never a scored mastery guarantee.

Use self-contained semantic HTML with inline CSS/SVG and bounded trusted local JavaScript. Escape all source excerpts/topic text as inert HTML text; use textContent for dynamic text. Do not interpolate topic input into executable script, innerHTML or executable templates. No eval, arbitrary learner-code execution, remote dependencies, fetch/file APIs, telemetry, credentials, clipboard, storage or operational command buttons. Ordinary deliberate http/https references may be links. A restrictive CSP is defense in depth, not a sandbox. Inspect the actual generated artifact and its script/data boundaries; the framework cannot enforce all future generated output.

Treat animated explanations as designed sequences. Before coding, sketch the learning beats: the initial state, the event, the visible consequence and the comparison that makes the idea click. Compose one coherent scene with clear visual hierarchy; keep an object recognizable as it travels, waits, changes or fails. Choreograph emphasis, stagger and pacing around those beats. Place short explanations beside the relevant action. Let the learner pause, replay and change a meaningful condition. Moving dots, pulsing cards, fade-ins and click-to-reveal text alone do not meet an animated-explainer request. Use a topic-specific visual metaphor rather than reskinning the routing example for everything. Keep controls subordinate to the explanation and preserve correct model state through every transition.

Keep units, finite bounds, assumptions and source/proposal status visible. Pause/step/reset meaningful timelines, stop hidden-tab loops, respect system and manual reduced motion, give keyboard/focus/touch access and narrow-screen layout. Include complete static worked states and print/no-script reasoning. Explicitly state reduced interactivity if tools/scripts are unavailable; never silently call a static substitute fully qualified.

## Inspect, ask, deliver

Inspect generated text and render/open locally using available authorized tools. Exercise meaningful state changes and feedback, narrow layout, keyboard, reduced motion and static fallback proportionately; report exact untested gaps. Rendering is not permission to install tools, execute application commands or deploy. A normal lesson needs no Tequio workspace, claim, mandatory reviewer or lifecycle gate.

Watch a complete animated sequence, not only a screenshot. Check whether the eye can follow the cause and consequence, whether transitions connect rather than obscure states, and whether labels remain readable while the scene changes. Inspect desktop and narrow-screen compositions. Revise visually weak output even when its controls and calculations pass; technical correctness does not establish visual quality. Never promise a particular aesthetic outcome or mastery solely from the template.

Once the temporary package is ready, ask one open-ended question: “Where should I keep this?” Suggestions such as a chosen vault folder or Desktop are examples, not an allowlist. Wait for the destination before external delivery. Reuse an already explicitly named destination without repeating the question; temporary preparation and verified copy still apply. Do not infer a personal vault from history.

Resolve and inspect the exact destination and every relevant parent/symlink boundary. Use a fresh collision-safe filename/package and exclusive creation, never overwrite or follow an unexpected symlink. Copy all bytes/assets, compare hashes and verify relative links before reporting delivery. If unsupported remote storage is named, check available authenticated tools and disclosure scope; do not reinterpret it as a local path, silently substitute another location or publish. Cloud-synced folders may sync under existing owner settings; do not alter sharing.

Keep the temporary source until delivery verification succeeds. Then remove only this invocation's known disposable staging if its identity/boundary/content are still safe; never clean arbitrary user directories. If failed transfer or uncertain cleanup leaves a duplicate, retain safe source, report the remaining path and do not claim a sole retained copy. No mandatory repository copy remains.

A vault can be the sole final home. Optionally include a Markdown summary with a relative HTML link for discovery. Storage in Obsidian does not imply in-note JavaScript execution; use a normal browser for interaction. Report whether actual desktop/mobile/vault opening was exercised. Never install plugins, change security settings or weaken the viewer to make it work.

Return final location, what the lesson explains, important evidence/limitations and any delivery duplicate. Return to the pending development question without automatically claiming/resuming work. Teaching does not authorize code/config/spec/dependency/task changes, installs, spend, operational execution, publication or acceptance receipts.
