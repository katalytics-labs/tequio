A load balancer chooses a destination. Capacity determines whether that destination can keep up. Those are different jobs.

The question to carry

When arrivals exceed the work your servers finish, where does the unfinished work go? By the end, explain why adding a server can help here—and why it cannot repair a shared database bottleneck.

What this represents

Assume three identical independent workers behind one router. This is a hypothetical teaching architecture, not evidence that your project implements or needs a load balancer. No repository implementation is asserted by this reusable example.

02 · observe the mechanism

Route → queue → process

Every step assigns arrivals in round-robin order, drops arrivals if the chosen queue already holds eight, then processes up to capacity on each enabled server. A full destination is not rerouted.

Changes apply at the next tick. Turning a server off drops its waiting work at that boundary.

03 · explain

Waiting is not yet loss.

With two servers and six arrivals, round robin gives each server three requests. Each completes two; one waits at each server. The accounting is 6 = 4 completed + 0 dropped + 2 queued.

Keep stepping: arrivals keep exceeding completions, so the queue grows. Once a destination already has eight waiting requests, its next arrival drops—even if another server has spare room. Routing policy matters as well as total capacity.

Worked states without the controls

Normal: three enabled, load 3, capacity 2: each gets one and processes one; no queue.

Overload: three enabled, load 12, capacity 1: first tick leaves three waiting per server; by tick 3, six new arrivals drop before processing and seven remain per server. Totals: 36 = 9 completed + 6 dropped + 21 waiting.

Failure: disabling a server drops its waiting queue at the next tick boundary. New arrivals go only to enabled servers. With none enabled, every new arrival drops. Reenable starts empty.

04 · transfer

What if the slow part is shared?

A different system has three web servers, all waiting on one database that can complete four queries per tick. Every request requires a query. Would adding a fourth web server necessarily increase completed requests?

Think about where the work is performed. This is a new constraint; the independent-server model above does not include a shared database.

Read the transfer answer

The shared database can still limit the whole path to four queries per tick. Adding frontends does not itself increase that limit. Measure the actual bottleneck before proposing a fix; caching, fewer queries or database changes each introduce different tradeoffs. No option is recommended for a real project without evidence.

Go deeper: what round robin leaves out

This finite model uses equal capacities, deterministic arrivals and immediate server enable changes. Real systems may use health checks, connection reuse, retries, weighted routing and different queueing locations. The model establishes none of their failure or consistency guarantees. More servers also add deployment and operational costs. A single adequately provisioned service can be simpler when current demand does not justify distribution.

Model boundaries and next question

Inputs are integer arrivals 0–12 and capacity 1–4, three server switches, queues bounded to eight, and 120 ticks. Invalid values clamp to bounds. Reset restores load 3, capacity 2, all servers enabled, empty totals and pointer A. Ask next: what evidence would show whether our real project's queue or shared dependency is the constraint?
