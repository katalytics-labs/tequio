# Evidence-backed milestone orientation

Status explains the road to usable outcomes using existing evidence. It is read-only guidance, not a milestone database, scheduler or semantic completion verifier.

## Select a small evidence set

Start with the explicit workspace’s current CLI status. Use an existing reviewed delivery plan, milestone map or approved brief and a recent relevant handoff to identify outcome groupings. Plans show intended scope; handoffs are dated claims. Cross-check consequential delivered/blocked/next claims against actual task details, current prerequisite/effective revision bindings and available acceptance evidence. Use targeted read-only `proof`, revision status or source inspection when necessary, not every receipt or all project history. No new planning artifact is required. If sources conflict or mapping is missing, say what is unknown and recommend one bounded reconciliation action; do not perform it during Status.

Keep traceability for consequential states with a concise project-source reference when useful. Do not expose raw evidence, prompts, credentials, claim tokens or private transcripts in summaries; an owner-facing local docket is not permission to copy project records into public reports or reusable framework assets.

## Compose honest states

| Evidence | Appropriate description |
| --- | --- |
| Completed task with historical checks | Recorded complete at that point; current prerequisite/acceptance may need inspection |
| Accepted backend, unfinished client | Backend implemented; end-to-end user journey partial |
| Reviewed design/mockup, owner approval absent | Design reviewed; owner direction pending; UI not implemented by implication |
| Isolated synthetic qualification, no device result | Qualified within that fixture; attended/device acceptance open |
| Task labelled ready but unmet dependency/changed binding | Ready specification, waiting on named prerequisite/current proof; not dispatchable |
| Draft | Read its actual sourced resolution before explaining; do not infer owner blockage |
| Explicitly deferred scope | Deferred with its recorded reason; not completed or automatically a blocker |
| Missing/contradictory mapping or evidence | Unknown/provisional; do not infer completion from counts |

Use project vocabulary and combine states where needed, rather than imposing a new state enum. In a larger docket, group older milestones only when their outcomes and qualifications can be summarized faithfully. Retain consequential unresolved acceptance within a grouped row. Do not resurrect superseded tasks or count old broad envelopes as separate remaining scope when successors already cover them. If successor coverage is incomplete/uncertain, report the ambiguity rather than deciding old scope disappeared.

## Response shape

Open with delivered behavior and current focus, actual blocker (or none recorded), and the useful next action. Follow with a small table: milestone/outcome, honest state, remaining acceptance or next step. Normally6–10 rows is a readability guide, not a mandatory quota or claim that only those outcomes exist. State a bounded view if further scope is omitted. Put task IDs behind outcome names as secondary references. Finish by connecting the immediate next action to the relevant row, including dispatchable/waiting distinctions and advisory checkpoint/unknown cost context when relevant. For a tiny project or explicit brevity, a sentence or short list suffices; next-action-only means just that action plus any essential blocker/authorization caveat.

Synthetic example, assuming the named plan and evidence actually support it:

| Milestone | State | Remaining acceptance / next step |
| --- | --- | --- |
| Save and retrieve records | Backend accepted; client partial | Connect the client’s save/retry journey |
| Navigation proposal | Design reviewed | Owner visual approval; application UI still unbuilt |
| Device capture | Synthetic checks passed | Attended device behavior not demonstrated |
| Reliable background processing | Ready specification, waiting | Refresh changed producer evidence before dispatch |

Next: reconcile the background-processing prerequisite before Build; the ready label alone does not authorize dispatch. This illustrative table is not evidence about a real project.

## Overnight or parallel questions

Only when asked, propose one or two outcome-sized slices whose prerequisites, resources and ownership can actually be checked. Explain why they are independent, or say independence is unknown. Read/write overlap and shared contracts serialize; separate folders or task names do not prove safety. Name required setup/current binding reconciliation and later owner/device/visual acceptance only where the project evidence establishes it. If those acceptance requirements are not recorded, label them unknown or conditional; do not assume every client needs device testing or every design needs a new approval. A due checkpoint is advice, claims do not establish live processes, and a lease expiry does not prove a worker stopped. Status never launches work, creates lanes, changes tasks/docs, recovers ownership, scans installation, requalifies specialists or grants resource/publication permission. Do not repeat qualification solely because a specialist was refreshed; inspect relevant binding/evidence first. Unknown usage and duration remain unknown.
