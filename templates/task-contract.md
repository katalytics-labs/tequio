# Detailed task contract

Task arrays import into one explicit workspace. `specialists` may be an empty list for generic work; nonempty labels identify qualified project-owned specialist packages. `id` is immutable; replan uses new IDs. Required fields are illustrated in task.json. `sources` are existing workspace-relative files, optionally with heading fragments. Requirements/contracts can be linked or excerpted into those artifacts. `reads` and `writes` are project-relative file/directory prefixes, no globs/traversal/symlinks or toolkit/VCS state. Write ownership serializes overlaps; readers also conflict with active writers. Declare shared contracts as resources, not prose-only assumptions.

`checks` are executable argument arrays, not shell strings; commands run from the project root in the inherited local environment, with private recorded output and timeout. Review commands before import: executing them is real code execution, not a sandbox. Every task needs acceptance criteria; review maps actual evidence to each criterion. `risk: security` additionally requires distinct security review. `stage: draft` preserves provisional work but is not dispatchable. Draft work becomes a new reviewed ready task through replan; do not edit SQLite manually.

Input fingerprints bind tasks to brief/analysis/spec/plan. Source Markdown needs substantive analysis, not empty templates or claims of prior work. Recording a phase proves file state, not quality. Domain contract changes require refreshed planning; do not quietly bypass staleness checks. Tests and reports bind to conservative project content snapshots. Dependencies must already exist or be in the same import; cycles fail. A task is done only with successful current checks plus independent current review and no findings.

Generated specialist IDs refer to the project registry. Ready tasks require current exercise-tested qualification, with exact revision/content/review bindings retained in authoritative task detail. `kind` defaults to implementation; research tasks may explicitly use `kind: research`. Research-mode specialists cannot implement selected product behavior. Draft tasks may name not-yet-qualified IDs. Generic tasks can keep specialists empty. Changing specialist/context requires explicit requalification/replan, not editing a claimed task.

Every ready task declares documentation impact: `{"mode":"update","paths":["docs/behavior.md"],"reason":"Specific behavior/contract impact"}` or `{"mode":"not-needed","paths":[],"reason":"Specific reviewed reason no docs change is necessary"}`. Update files belong in declared write ownership. Implementation updates them alongside behavior, verifies actual results, then records a private reconciliation covering every task source and doc path before fresh correctness review/closure. The template is documentation-report.json; no extra user skill is required.

Ready tasks also declare `security_assessment`; nonempty surfaces require security risk. `kind: release` requires security risk, concrete owned `candidate_paths` and structured independent security coverage. Read `../skills/tequio-tasks/references/security-workflow.md` for schema, candidate freshness, migration and limits; use release-task.json and release-security-report.json.


## Explicit bounded verification capture

New task/release templates opt into `capture:{version:1,mode:"bounded-v1",max_bytes:1048576}`. Exact keys, integer version1 and byte limit1..16777216; booleans/unknown supplied fields are invalid even on new drafts. The budget is shared across both streams/all check attempts, never reset per check. Absence preserves legacy task/API/receipt/timeout behavior; imported history is not migrated. This is capture policy for reviewed task commands, not a global tool sandbox or automatic security classifier.

Bounded mode concurrently drains nonblocking pipes in chunks at most64KiB. Exactly the budget followed by EOF completes; an additional byte terminates the owned group and aborts unattempted checks. Timeout/read failure likewise retains captured prefix and stops later checks. Human-readable UTF-8 replacement strings and base64 raw prefixes are stored privately. Budget bounds retained raw payload, not all task metadata/host memory. observed_bytes stops at terminal capture decision; subsequent cleanup bytes have separate accounting. No truncation may yield a full-evidence PASS, including a process that already exited zero.

Bounded receipts use schema_version2 and include policy, retained/observed/cleanup byte accounting, capture state/completeness, planned/attempted/executed counts and ordered skipped indexes. Results contain attempts, original indexes, launched booleans, actual observed exit codes, previews and exact stream byte/base64 counts. Launch failure remains an attempted result with no child; ordinary failures do not stop subsequent checks. Limit/timeout/capture failure skips only never-attempted checks. Version-aware readers validate policy, lengths, counts, raw/preview consistency and outcome before trusting passed. Unknown/inconsistent versions are invalid; valid incomplete capture is failed. Acceptance still requires current source/input hashes, docs and actual required independent reviews.

Only bounded summaries use schema_version2: existing top-level summary fields plus capture `{state,complete,max_bytes,retained_bytes,planned}`; checks is `{attempted,executed,passed,failed,skipped}`. attempted counts result entries, executed counts spawned children; passed+failed=attempted. New fixed codes capture-limit-exceeded/capture-failed join existing nonzero/timeout/launch/instability codes; first3diagnostics plus omission count remain. No raw/base64/argv/error prose is included. Legacy summaries remain version1 unchanged. Metadata is private operator data, not a public export.

Bounded receipt readers/writers enforce `8*max_bytes+1048576` serialized bytes, including size checks before JSON/base64 decode. Oversize metadata or publication failure attaches no result; an older PASS cannot substitute. Successful complete verification exits0, published failure exits1 and infrastructure/uncertain cleanup exits2. Exact path/hash publication stays under the operation guard. No spooling, automatic retention/deletion, global rollout or specialist/Git-command capture change is included.

## Refinement and bounded investigation

[Revision](../skills/tequio-tasks/SKILL.md#standalone-revision-reference) may replace selected unfinished definitions and explicitly rebind unchanged unowned consumers. Original definitions remain immutable; effective dependency/input history is separate and new bindings require new current proof. Changed checks/acceptance/contracts require new IDs. Completed nodes require reviewed successors, never historical body/receipt edits. Add-only tasks use ordinary reviewed import.

For independent policy/functional work, assess disjoint actual scoped-v1 reads/writes/shared/config resources and join both at final integration; overlap and genuine dependencies remain conservative. There is no semantic/file-type exemption or old-PASS reuse.

An uncertainty may use optional experiment.md to define product blockage, reuse, faithful observations/effects, ceilings, decision and next slice. Complete sufficient observations are needed for supported/unsuitable; missing input/budget is unqualified. Keep this guidance out of mandatory task schema. Distinguish cheap feedback/focused rechecks from stable required independent reviews and final combined proof.
